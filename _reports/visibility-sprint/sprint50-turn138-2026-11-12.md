# Turn 138: Make source-backed project fragment arrivals identifiable

Date: November 12, 2026

Baseline: `73a36e764eadad412ae68b62a9c0eab544b46d3a`

## Observed navigation gap

Turn 137 gave homepage visitors a direct route to the documented fictional
double-charge example inside Review Reply Writer. A live 390-pixel browser
check confirmed that native navigation arrived at the correct heading below
the persistent header. The heading looked like ordinary page text, however,
without the visible arrival outline already used on key homepage and
Technology method destinations. A reader landing partway through a long
case could miss which section the link had selected.

Other public pages also link to the case's `#reply-boundary` and
`#reply-failure` sections. Each uses a native heading ID and deserves the
same quiet arrival cue. This is an observed orientation affordance, not
evidence of visitor drop-off, higher rankings or reduced confusion.

## Improvement

- Add one page-scoped `:target` rule to the existing workflow stylesheet.
  It applies a two-pixel red outline with four-pixel offset to a selected
  `h2` section heading inside the recorded Review Reply Writer case.
- Cover all current and future case section headings that use a native
  heading ID, including the three independently linked examples, owner
  controls and archived failure sections. Keep normal headings unoutlined.
- After the first publication, inspect all twelve fragment destinations in
  the live narrow-screen browser. This exposed a separate settling problem:
  later headings could finish above the sticky header, even though the native
  scroll padding was present. The lowest section finished 404 pixels above
  the viewport in that check. Do not mistake a visible CSS outline for an
  actually visible destination.
- Add a small deferred script only to the Review Reply Writer case. After
  load and local fonts settle, it checks whether the selected heading is
  obscured or below the visible area. Only then does it align the heading
  below the sticky header, without taking keyboard focus. Keyboard, pointer,
  touch, wheel and page-exit events cancel the pending correction. Ordinary
  fragment IDs, URLs and reader navigation stay intact.
- Register that content-versioned script in the case builder and public live
  file comparison. It makes no network requests, stores no reader data,
  adds no trackers, and does not alter any source claim or publication date.
- Protect the behavior with six focused tests for scoped CSS, the three
  distinct inbound fragments, stable source evidence, content-versioned
  stylesheet and script references, cancellation safeguards, publication
  metadata, and deliberate negative controls. Add the tests to the local-only
  release checklist.
- Retain the project's historical archived result text, original article
  date, canonical URL, Person identity, and public source links unchanged.
  No GitHub Actions, paid services or private materials were introduced.
