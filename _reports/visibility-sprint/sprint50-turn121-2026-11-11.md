# Turn 121: Confirm selection before promising manual Copy

Date: November 11, 2026

Baseline: `8c24dd671d0f91c2a3acb3727bbcf94362d4cb7e`

## Observed logic problem

The Task Brief builder's **Select text manually** route always told the
reader the complete brief had been selected immediately after calling the
browser's `textarea.select()` method. The old code did not inspect the
actual range or catch a selection exception. On a device where programmatic
selection is ignored or rejected, that assertion is not warranted, and an
exception could interrupt the fallback entirely. This is a code review and
fault-injection finding, not a claim of an observed production-device failure.

## Improvement

- Attempt focus and native text selection without allowing an exception to
  remove the entire recovery route.
- Report that selection succeeded only when the actual text-control range
  starts at zero and ends at the complete assembled text length.
- If full selection cannot be confirmed, show a short warning both next to
  the field and in the nearby fallback group's accessible label. Supply
  explicit **Ctrl+A/Cmd+A**, **Ctrl+C/Cmd+C**, and touch **Select all, Copy**
  instructions, and direct the reader to paste elsewhere to verify.
- Preserve the honest warning through subsequent keyboard or pointer events
  unless a full selection really occurs. A genuine native **Select all**
  transition restores the original selected-but-not-copied state.
- Keep existing Save and Print recovery options when available and retain
  Turn 120's memory of known failed export routes.
- Add an isolated Node-driven test of a no-op `select()`, a throwing
  `select()`, native reselection, accessible text, and field-edit reset.
  Register it in the manually run site release checklist.

No new tracking, storage, remote data transfer, dependency, recurring job,
or GitHub Actions is introduced. Assembled text, existing URLs, document
structure, and the November 11 page revision date are unchanged.
