## Reader-path audit

Two existing Technology articles answer adjacent practical questions, but
neither linked directly to the other:

- `/technology/ai-website-visibility/` records public website changes and
  explains how to check search outcomes separately from publication.
- `/technology/checking-ai-website-changes/` records an October 11 HTML
  parsing defect that the earlier test suite did not detect.

Both are independently documented cases on the same public website. A reader
learning how to verify a release may also need the distinction between
release quality and search performance, and vice versa. The previous route
required finding the related article through some other part of the site.
This observation comes from the local source and generated pages, not from
Search Console, referral logs, or measured reader behavior.

## Change

- Added one descriptive contextual link from the search-visibility case to
  the earlier website-verification case. The copy identifies the October 11
  defect and explicitly separates it from the November 5 channel-route
  verification and unmeasured ranking outcomes.
- Added one contextual return link from the verification case to the
  visibility case and its free local Search Console CSV measurement method.
  The copy explicitly says the later work did not retroactively measure the
  October 11 repair.
- Used ordinary crawlable anchor links to the articles' existing canonical
  URLs. No tracking parameters, redirects, new scripts, or external services.
- Preserved original publication and revision dates because adding the
  brief reader navigation is not a major content revision. Existing case
  claims, source trail, and page titles remain unchanged.
- Added a dedicated regression test with deliberately broken-link and
  misleading-evidence negative controls, and registered it in the manual
  local release checklist.
