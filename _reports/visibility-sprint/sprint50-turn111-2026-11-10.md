# Turn 111: Acknowledge manual Copy attempts without claiming success

Date: November 10, 2026

Baseline: `fd5d77f489fc919c6d883fa08f50f0f6dfd42480`

## Observed reader problem

The Task Brief Builder correctly warned readers that selecting its
complete text was **not** a copy. But after a reader used the browser's
native **Copy** command, the adjacent cue still said **"Selected, not
copied."** The stale cue could imply that the user had skipped the
action even though a copy command had been attempted.

A native browser `copy` event is evidence that the command was
triggered. It does **not** verify that the system clipboard now
contains the correct text, so no successful-copy claim is justified.

## Improvement

- When the manual-copy cue is visible and the entire read-only brief
  is selected, respond to its native `copy` event with the adjacent
  message **"Copy command detected. Paste to check the result."**
- Update the existing polite status region to explain that the page
  cannot confirm clipboard contents and ask the reader to paste and
  verify the result before leaving.
- Do **not** intercept the native Copy command, read the clipboard,
  make a second clipboard write or report unverified success.
- Ignore a partial selection, a hidden cue or an invalidated result.
  Reset the original selected-only instruction on a new selection,
  edit, assembly, automatic copy, print or download.
- Add two new local regressions that execute the production event
  handlers, check state transitions, verify that Copy is not
  intercepted, and check the generated JavaScript fingerprint.
