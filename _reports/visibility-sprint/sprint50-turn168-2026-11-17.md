# Visibility sprint Turn 168: Section-matched navigation for poker practice

Date: November 17, 2026 (America/Phoenix)
Baseline main: `120c1f90ef7e44c026c9735a25a02d1701c26988`

## Reader problem confirmed on the published HTML pages

Turn 167 already replaced the raw Markdown reading experience with
two formatted, mobile-oriented, script-free HTML views. A read-only
live browser audit confirmed proper headings, seven numbered sections,
fourteen vertical answer cards, five local checking boxes, and working
top/bottom links back to the questions.

The same audit exposed a more specific navigation defect. Neither
HTML view had internal section IDs or step-jump links. A reader who
wanted to compare practice question 5 against answer-key section 5
had to scroll down through the earlier content on both pages, then
start over at the top when returning from the key. This creates
unnecessary scanning work during the very activity the content is
supposed to teach.

The live browser did **not** resize to a mobile viewport, so this
was a real missing-navigation defect, not proof of horizontal
overflow at 320 or 390 pixels.

## Improvement completed

### Seven matched section anchors

On the formatted practice page,
`/downloads/poker-hand-review-practice-01.html`, added:

- `#case` for the complete fictional scenario.
- `#question-1` through `#question-7`, exactly once each.
- A compact native `nav`, labeled **Jump to a practice step**,
  with Scenario and seven numbered study topics.

On the formatted checking key,
`/downloads/poker-hand-review-practice-01-key.html`, added:

- `#check-1` through `#check-7`, exactly once each.
- A matched native `nav` labeled **Jump to a checking step**.
- One distinct **Compare with question N** link immediately after
  each key section heading. Each targets the corresponding
  `/downloads/poker-hand-review-practice-01.html#question-N`.

Existing top and bottom **Return to questions** links still
work. The additional section-specific links make it possible
to compare one question without always restarting the exercise.

### Accessible, responsive presentation

Each page receives the same small embedded CSS rules for step
navigation, with two flexible columns on narrow layouts and four
on wider layouts. The links provide at least 44px minimum touch
height, wrapping labels, a visible keyboard outline and a
contrasting `:target` highlight on the destination heading.

The jump navigation and compare links are excluded from print
output, leaving the underlying questions and key readable on
paper. No page scripts, remote styles, remote fonts, forms,
cookies, background calls or storage were added.

### Strict content and publication boundaries

The original question and checking-key Markdown downloads are
**byte-identical** to Turn 167. Their existing Git blob source
fingerprints remain correct on both HTML views. Every numerical
answer remains in the checking key, not in the question page.
The practice page still contains exactly one link to the key
only **after the Stop here** barrier.

Neither page changes its seven question/checking headings,
fourteen answer cards, five checkboxes, explanatory paragraphs
or calculated chip amounts. The two HTML documents remain
`noindex,follow` alternate reading views, not independently
published article routes.

The general hand-review guide, its dates, the private blank
worksheet, three completed real-hand reviews, site manifest,
sitemap, feeds and local Find index are unchanged.

## Regression coverage

New `_tests/test_turn168_practice_anchor_journeys.py`
checks the exact eight/seven nav targets, unique headed sections,
matching Markdown source headings and fingerprints, all seven
section-specific return URLs, script-free markup, target
visibility CSS, print-only hiding, the five checking boxes,
fourteen answer cards, and absence of key links before the
question stop barrier. Negative mutations cover missing
anchors, wrong step targets, a removed stop barrier, a
missing highlight and incorrectly numbered return links.

Updated `_tests/poker_review_readable_browser.py`, the
existing optional offline full-HTML Chromium test, to exercise
a **real click** on the step-5 fragment on both pages and
verify a highlighted, in-viewport destination without document
overflow. It also checks all seven return links on the key
at 320, 390, 768 and 1440 pixel widths.

The new Python regression is registered in
`_scripts/local_release_checks.py`. No GitHub Actions,
other CI, cron, paid service or ongoing monitoring was created.

## Verification actually performed

1. **Live browser audit, before changes:** confirmed
   formatted page rendering and the missing step-jump/return
   paths. Default desktop inspected; no controlled mobile
   viewport available.
2. **GitHub source checks, on branch:** verified one-to-one
   targets, eight question navigation links and seven key
   links, seven direct key-to-question returns, source
   fingerprints matching the unmodified Markdown blobs,
   unchanged answers and barrier, and the release registration.
3. **Isolated local Chromium layout experiment:** exercised
   the new responsive step-navigation CSS with representative
   long question sections at 320, 390, 768 and 1440px.
   Real link activation took the browser to `#question-5`;
   the target received a solid highlight outline, and no
   horizontal document overflow was seen in that fixture.
   This is a **CSS/interaction fixture**, not a full production
   page test.
4. **Byte-for-byte source scope:** confirmed the Markdown
   downloads, authored and published main hand-review guide,
   private blank worksheet, manifest, sitemap, both RSS
   feeds and Find index are unchanged.

**Not executed:** the complete Python site build, full
unittest suite, full committed-HTML Playwright runner,
real phone or screen-reader audit. The connected repository
is accessible through GitHub tools but is not mounted
as a local checkout in this environment. The fixture
result is not a complete 320px production-page certification.
