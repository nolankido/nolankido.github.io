# Turn 142: Correct AI project deep-link arrivals earlier

Date: November 12, 2026

Baseline: `64c1d81eb4dedd3488e6316a37a359d7b7485b78`

## Observed problem

Turn 141 introduced a visibly outlined, scoped native fragment destination
for three practical AI project pages. A direct Chrome check at a 320-pixel
viewport found the Preflight example heading temporarily covered by the
roughly 149-pixel sticky header at an approximately 1.75-second observation,
before it corrected by the three-second check. The script's only adjustment
waited another 1300 milliseconds after page load and font readiness.

This was an observed timing issue on one direct arrival, not evidence that
every browser hid the heading or that search and engagement suffered.

The first published revision in [PR #300](https://github.com/nolankido/nolankido.github.io/pull/300)
added a correction on the next animation frame. A subsequent live Chrome
320-pixel check found Dinner on Time corrected quickly, but Preflight could
still remain at approximately 82 pixels even 1.6 seconds after navigation
had returned. The first frame alone therefore did not meet the observed
Preflight goal. A browser restoring its native fragment position after that
frame is one possible explanation, but has not been independently proven.
After [PR #301](https://github.com/nolankido/nolankido.github.io/pull/301)
added the 240-millisecond recheck, a fresh live Preflight navigation was
visible at first and at the 350-millisecond sample, but back near 82 pixels
at the later approximately 800-millisecond sample. It became visible again
after the final delayed check. The later repositioning requires a check
triggered by the actual browser scroll rather than another guessed delay.

## Improvement

- Keep waiting for page load and font readiness, then check the selected
  heading on the next animation frame. If the heading is under the sticky
  header or near the viewport bottom, bring it into view promptly.
- Recheck after another 240 milliseconds, to accommodate delayed native
  fragment positioning or a skipped frame. Only reposition if needed.
- During the bounded arrival window, also check browser-driven `scroll`
  events with a passive listener. This handles a native restoration that
  occurs *after* the two early checks; an already visible heading is not
  moved. The listener is removed by the same abort mechanism.
- Preserve the 1300-millisecond final check to account for late layout
  shifts, including elements that move after the first two checks.
- Preserve the existing exact fragment and case-page allowlist, visibility
  threshold, instantaneous scrolling, and native focus behavior. Keyboard,
  pointer, wheel, touch or page-exit interaction cancels the pending
  animation frame, both timers and the scroll listener. Hash changes also
  cancel stale checks.
- Keep the shared script scoped to the Review Reply Writer, Preflight and
  Dinner on Time case pages. Rebuild only their versioned script references.
  No content claims, article dates, canonical URLs, schema facts, tracking,
  personal data, paid services, CSS or automated workflows changed.

## Publication and live verification

- [PR #300](https://github.com/nolankido/nolankido.github.io/pull/300)
  added the first-frame correction. The live check identified a subsequent
  Preflight failure, so [PR #301](https://github.com/nolankido/nolankido.github.io/pull/301)
  added a short post-arrival check. The next trace identified still-later

  added the bounded passive scroll listener. Each PR was squash merged after
  passing the full local suite, with a remote tree identical to the local
  reviewed tree. The final code merge is
  `757be73c2ceba7e8c4bdf2fa492004c56658e480`.
- After final deployment, direct GETs for the script and all three case-page
  HTML files matched local SHA-256 bytes. The pages referenced the final
  content-hashed script `v=39dbe9bca000`.
- Live Chrome at **320 pixels**: nine sampled observations on a fresh
  Preflight deep link, approximately 0.5 to 2.0 seconds after navigation
  returned, all showed the selected heading near **180px**, below the
  approximately **149px** sticky header. The red outline remained visible,
  and there was no horizontal overflow. A cache-busting query was used to
  ensure this trace tested the final deployed page instead of the older
  version retained by the connected browser.
- Live Chrome at **320 pixels**: Dinner on Time's demo and Review Reply
  Writer's failure heading both settled around **180px**, with the same
  header clearance, solid target outline and no horizontal overflow.
- Live Chrome at **1440 pixels**: Preflight's example heading settled near
  **100px** below a roughly **76px** header, with the outline visible and
  no horizontal overflow. The temporary browser viewport override was
  reset after testing.

These observations do not establish universal browser behavior, prove why
Chrome performed the earlier late scroll or demonstrate changes in search
visibility, engagement or retention.
