# Visibility sprint Turn 167: Mobile-readable poker practice and checking key

Date: November 17, 2026
Baseline main: `39f724dd10cfdefe558a910c6d8d3dba56d83591`

## Reader problem, observed on the live site

A read-only live browser audit of the existing practice flow confirmed that
the guide's **Try a new case** link opened
`/downloads/poker-hand-review-practice-01.md` as **raw, unformatted
Markdown** in the browser. Literal heading markers, double asterisks,
pipe-delimited checking-key tables and Markdown link syntax were visible.
The links were not rendered as clickable browser links. A first-time reader
therefore needed to interpret Markdown syntax and rely on the browser Back
button to return to the questions. No file download automatically started.

The live automation did **not** change its viewport to 390 pixels. Therefore
horizontal overflow on an actual phone was not directly established by that
audit; the narrower-screen concern was a plausible design risk, not a
confirmed production failure.

This was a delivery and usability problem, not a missing poker solver.

## Reader improvement delivered

### Two browser-friendly, no-script HTML readers

Added:

- `/downloads/poker-hand-review-practice-01.html`: seven-step question
  sheet plus the opening fictional scenario, with real, readable headings,
  lists, emphasis, clickable links and a separate checking-key link **only
  after the Stop here barrier**.
- `/downloads/poker-hand-review-practice-01-key.html`: the existing
  arithmetic and evidence key, presented with **14 vertical cards**
  (five evidence-label claims and nine chip-ledger checks) rather than
  two horizontally wide Markdown tables. It has five functional native
  checkboxes, visible labels and prominent **Return to questions** links
  in the header and below the explanation.

Both pages use the existing Nolan Kido site's cream, basalt and red
palette, but are designed as auxiliary reading views rather than new
standalone articles. They use a small self-contained stylesheet with
mobile-width rules, flexible wrapping, visible keyboard focus,
a skip-to-content link, 44px target minimums, and print styling.

There is **no JavaScript, external font, external script, image, form,
payment integration, tracking, analytics or storage**. The content
security policy disallows external resources. HTML metadata sets
`noindex,follow` because these are alternate formatted views of
existing Markdown downloads, not competing SEO articles or newly
dated main-website pages.

The `.md` question and key files are **byte-for-byte unchanged** and
remain available through explicitly labeled `download` links for
private editing and offline reading. Every generated reading view
stores its source file's Git blob SHA, verified by a local Python
contract so a future Markdown change cannot silently leave an HTML
reader stale.

### Navigation improvements

- The hand-review guide's existing **Try a new case** link now opens
  the formatted question page, not raw Markdown.
- The private seven-step worksheet prioritizes the HTML reading
  experience and separately retains the editable Markdown question
  link.
- The checking-key page offers both a top-navigation and a
  bottom action to return to the formatted questions.
- The key is **not** linked in the guide or private worksheet,
  and the practice page contains no computed ledger answers.

The guide's original six-section outline, approximately four-minute
reading time, fictional K-Q example, source documented hand links
and publication dates remain unchanged. `_source/pages.json`,
sitemap, RSS, Find index and all three completed hand examples remain
byte-identical to the baseline.

## Evidence collected this turn

1. **Real public browser:** raw Markdown renders without formatting and
   with visibly unrendered links, for both the questions and key.
   The observed default desktop path had no dedicated return
   navigation from the bare Markdown key. The browser tool did not
   support a controlled 390px viewport.
2. **Committed source checks:** both new HTML files have one H1 and
   all seven ordered review steps (eight H2 headings total on
   the question view because the fictional-case introduction is
   also a section). The checking key has fourteen labeled cards
   and five local checkboxes. The key's link is only after the
   questions' Stop here barrier; no calculated ledger answer
   appears in the question view.
3. **Source fingerprint:** the question's HTML records Git blob
   `2a5ef855fe0ed12ababe3ce2a4ef7a85dbee0409` and the key
   records `8bafdfd31e91f7e3e630f7ea21a9fa52e5c934fb`,
   matching the unchanged Markdown files.
4. **Diff and historical parity:** only the guide's href and the
   worksheet's two practice-entry lines changed. Old documents,
   full source and public guide parity, metadata, search and
   feeds remain intact.
5. **Local Chromium style reproduction:** using the exact
   4,214-character responsive stylesheet from the generated key
   and representative long checking-key cards, the viewport
   and card boundaries remained within the document at **320,
   390, 768 and 1440 pixels**, both at normal and 200% text
   sizing. This was an **isolated layout fixture**, not an
   execution of the complete committed HTML browser script.

**Not executed here:** full repository Python build, complete
historical unit suite, or the complete new in-memory full-HTML
browser runner. The connected GitHub repository is not mounted
as a local checkout in this environment and container DNS
cannot clone it. Do not present fixture results as full-page
or real-phone certification. The live public flow after merge
should be tested separately, with viewport resizing still
unverified unless a capable browser is available.
