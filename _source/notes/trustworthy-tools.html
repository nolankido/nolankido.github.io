Two calculations can agree and still make the same mistake. Agreement becomes evidence only after asking what, exactly, is being checked.

A claim small enough to check

Consider a fictional tool that summarizes how long a task takes. Its stated job is to report the median: sort the observations and take the middle one, or average the two middle values when there is an even number. The interface calls this the typical duration.

For observations of 2, 4, and 6 minutes, it reports 4. That looks right. A second implementation reports 4 too. It is tempting to call the result independently verified.

Now give both implementations a different input: 2, 2, 2, 2, and 22 minutes. Both report 6.

Input: 2, 2, 2, 2, 22.

Median: 2, the middle observation.

Arithmetic mean: (2 + 2 + 2 + 2 + 22) / 5 = 6.

What happened: both implementations computed the mean and labelled it the median.

Neither statistic is inherently wrong. They answer different questions. The defect is reporting one as the other. Agreement on the first input hid the defect because the mean and median happened to coincide.

Independent code is not always an independent check

A second program written in a different language would not solve this problem if its author copied the same mistaken definition. Two implementations can be separate while sharing the assumption that matters most.

The useful independent check here is a definition and a small example worked out without relying on either implementation. Sort five values, find the third, and compare that answer with the displayed result.

This distinction also applies to explanations. Rephrasing a claim, asking another system to endorse it, or obtaining the same answer twice does not automatically add new evidence. Ask whether the second route could fail for the same reason as the first.

Test a boundary, not just another comfortable example

Once the median calculation is corrected, several questions remain. Does it sort its input? What happens with four observations, such as 2, 4, 6, and 8? Does an empty list produce a clear refusal rather than a made-up duration? Are missing observations rejected, ignored, or represented explicitly?

For this illustrative specification, valid inputs are nonnegative whole-minute observations. Missing entries, text, negative durations, and an empty list are rejected. Other specifications are possible; what matters is choosing one before interpreting the result.

The Python unit-testing documentation describes a test case in terms of a particular response to particular inputs. That narrowness is useful. A passing test establishes something about the behavior tested, not everything the interface might lead a reader to assume.

A correct calculation can still support the wrong conclusion

Suppose the corrected tool reports a median of 2 minutes for the five observations. The calculation is now right. It still does not establish that a new task will take 2 minutes, that the observations are representative, or that the occasional 22-minute task can safely be ignored.

The long task may matter more than the middle task when making a promise. If it is a data error, that needs its own justification. A correct formula cannot decide those questions on its own.

A report worth relying on would identify the statistic, show how many observations it summarizes, and make important exclusions visible. A decision might require a different summary altogether.

Make the evidence fit the consequence

A rough estimate for arranging a draft can be useful before every uncertainty has been resolved. A system used to make an expensive or irreversible promise deserves a different standard. The display should not make those standards look interchangeable.

Start with the claim, find a small case that could expose a mistake, and separate the calculation from the interpretation. The aim is not endless checking. It is knowing which conclusion the evidence actually supports.

The next useful question is not just “Does it work?” It is “What, exactly, have we established?”
