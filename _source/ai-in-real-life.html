Nolan Kido / Applied AI portfolio

What does using AI in real life actually look like?

I use AI to build software, check source material, and prepare work that still needs a human decision. These examples are not interchangeable: a repaired live website is evidence of actual delivery, while a fictional customer reply, proposed video graphic, and cooking simulation prove narrower things. Follow the public records and judge the work for yourself.

My rule: AI Works, Human Decides. Define the task, check the result against independent evidence, and keep approval, permissions, and consequences with people.

01 / Flagship recorded case

Building and checking a real website.

The problem: An AI-assisted website release appeared ready after its build, search audit, and 347 unit and content tests passed. An independent HTML5 parser found a malformed closing tag. The correction was made before the release went public.

Task / A real public website

Improve a site without losing its integrity.

The change concerned public search presentation, authorship, breadcrumbs, and an explanation of the AI Task Brief Builder. A useful release had to preserve working pages and accurate public claims, not merely produce plausible markup.

The build passed, but the HTML was malformed.

On the task-brief page, the HTML5 parser identified end-tag-too-early for div. A browser may recover from a mismatched closing tag, so apparently normal rendering and other passing tests were insufficient evidence.

Corrected source, checked delivery.

The historical repaired candidate passed 347 unit and content tests and 21 browser suites. After publication, 235 sampled public GET targets matched the expected release responses. These are recorded checks, not measurements rerun for this portfolio.

What this proves, and what it does not.

Established: An AI-assisted real-world change contained a structural HTML error; a different check exposed it; a source correction was made; and the recorded release checks covered the corrected site. Transferable lesson: Match independent checks to different risks. A deterministic build verifies consistency, an HTML5 parser checks document structure, functional browser tests sample behavior, and a public response comparison checks what was actually served. 02 / Public submission and local demonstration

RightsReceipt: AI proposes terms, people approve.

The practical problem: A creator receives a request to use an image in advertising. Before money changes hands, someone must establish the scope, resolve contradictory terms, approve a price and distinguish payment evidence from a convincing-looking receipt. RightsReceipt turns that problem into a reviewable workflow with explicit decision boundaries.

Problem / Incomplete rights requests

Make an ambiguous request specific.

The fictional Harbor After Rain example separates territory, channels, duration, editing rights and other conditions. The proposal is priced at USD 425.00 by a deterministic creator policy. This is an illustrative quote, not an actual sale.

Human control / Separate authority

Let AI suggest, not authorize.

A source-grounded extractor and a local lexical classifier propose fields and flag uncertainty. The creator must approve rights, the buyer must accept the exact terms, and authoritative PayPal evidence would be needed for payment. Model predictions cannot set prices or grant permission.

Delivery / Public, inspectable prototype

Publish a demonstration and testable source.

The Devpost submission, public video and pinned open-source checkout document a completed hackathon submission. Local payment-like responses remain explicitly simulated.

What can visitors independently inspect?

  1. Public submission: RightsReceipt on Devpost describes the submitted project, its code, video and known limits. A submission is not proof of an award, production adoption or payment settlement.
  2. Reproducible source: The pinned judge guide documents a local console using Node 22.13 through 22.x. Its functional smoke source checks three application-handler journeys, three resets and zero external requests, with paymentEvidence: "simulated_only". The project reports that these tests passed in its historical submission checks; I have not independently rerun the Node suite for this website update.
  3. Actual AI inference: A separate read-only classifier proof operates on two synthetic requests across 24 rights-field comparisons. The model makes a known conflicting territory suggestion when a request also says Germany only. The diagnostic flags the conflict for a person instead of silently treating the prediction as approved rights. Its payment evidence is none.
  4. Viewer-facing demonstration: The public video is an edited demonstration, not uninterrupted evidence of a real PayPal Sandbox payment or a signed legal license.

What did this project not establish?

The submission establishes a public artifact and inspectable implementation, while its documented local runs support narrower software-test claims. They do not establish verified copyright ownership, authenticated creator identity, a separately paid PayPal Sandbox invoice, a validated paid webhook, enforceable real-world permission, production reliability or actual customer adoption. A receipt hash detects byte changes; it does not prove the underlying assertions were true.

The transferable AI lesson: Put model suggestions beside source evidence, let a person resolve uncertainty, use deterministic code for commitments such as pricing, and require the appropriate outside authority to confirm outcomes. A realistic demonstration is useful, but simulated financial state must remain labeled as simulated.

Method / Measure the real task

What would it take to prove AI actually helped?

Measure preparation, generation, checking, repair, maintenance, and human approval. The first successful output is not the whole task, and an estimate is not an observation.

  1. Define the task and permitted inputs. Create an AI task brief.
  2. Preserve a credible non-AI baseline. Use a controlled workflow pilot.
  3. Verify important claims and numbers. Apply the source and arithmetic checks.
  4. Count human review and rework. Compare full workflow time.
  5. State the evidence level. Distinguish simulation, repeatable prototype, public release, repeated real-world use, and independently measured impact.
