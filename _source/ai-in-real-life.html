What does using AI in real life actually look like?

I use AI to build software, check source material, and prepare work that still needs a human decision. These examples are not interchangeable: a repaired live website is evidence of actual delivery, while a fictional customer reply, proposed video graphic, and cooking simulation prove narrower things. Follow the public records and judge the work for yourself.

My rule: AI Works, Human Decides. Define the task, check the result against independent evidence, and keep approval, permissions, and consequences with people.

01 / Flagship recorded case

Building and checking a real website.

The problem: An AI-assisted website release appeared ready after its build, search audit, and 347 unit and content tests passed. An independent HTML5 parser found a malformed closing tag. The correction was made before the release went public.

Task / A real public website

Improve a site without losing its integrity.

The change concerned public search presentation, authorship, breadcrumbs, and an explanation of the AI Task Brief Builder. A useful release had to preserve working pages and accurate public claims, not merely produce plausible markup.

Failure / A different check disagreed

The build passed, but the HTML was malformed.

On the task-brief page, the HTML5 parser identified end-tag-too-early for div. A browser may recover from a mismatched closing tag, so apparently normal rendering and other passing tests were insufficient evidence.

Outcome / Recorded release

Corrected source, checked delivery.

The historical repaired candidate passed 347 unit and content tests and 21 browser suites. After publication, 235 sampled public GET targets matched the expected release responses. These are recorded checks, not measurements rerun for this portfolio.

Follow the original evidence from failure to release.

  1. Before the repair: At pinned source revision 2bf8908, the actual final closing sequence was </div></div></section>. The extra closing container is visible in the archived file.
  2. After the repair: At pinned revision 73782ca, the sequence was </div></section>. The commit comparison includes other work too; this is the specific source difference checked for this case.
  3. Release verification: Merged release PR #40 and its referenced check records document the repaired candidate, browser suite, deployed release, and public-byte comparison. The compact evidence record preserves the identifiers and the limits of those historical results.

What this proves, and what it does not.

Established: An AI-assisted real-world change contained a structural HTML error; a different check exposed it; a source correction was made; and the recorded release checks covered the corrected site. Not established: How much time AI saved, improved search rankings, increased business revenue, complete accessibility or security, or error-free future releases.

Transferable lesson: Match independent checks to different risks. A deterministic build verifies consistency, an HTML5 parser checks document structure, functional browser tests sample behavior, and a public response comparison checks what was actually served. No single check covers the whole task.

Use the evidence yourself: Read the full historical case and reduced reproduction, download the free offline release-check runbook, or inspect the small parser example. The example reproduces the failure class, not the full archived release.

A separate, later question: Did the site's 25-turn search-visibility sprint improve discovery? Its public change ledger confirms releases, but Google performance and assistant citations were not measured in the sprint. These outcomes must not be inferred from a clean deployment.

02 / Measured model stage, unmeasured productivity

Drafting customer replies without giving AI authority.

Review Reply Writer explores a small-business task: draft a customer reply while keeping the owner responsible for what is actually posted. The local Gemma tool distinguishes a customer's reported experience from verified policy and the exact wording requiring human approval.

What a real local model test actually measured.

On October 13, 2026 Hawaii time, a retained three-case evaluation ran gemma3:4b through Ollama on a GitHub-hosted Ubuntu CPU runner, not on my Windows laptop. The reviews were fictional, developer-written fixtures. The case_elapsed_ms values in the pinned raw results were:

  1. Cafe praise: 19.536 seconds, one model attempt.
  2. Cafe complaint: 18.157 seconds, one model attempt.
  3. Mixed hotel stay: 19.325 seconds, one model attempt.

The arithmetic mean of these three selected case elapsed times was 19.006 seconds. All three passed that historical version's automated checks on the first attempt. These are real recorded machine-stage timings, not measured human time saved, a representative benchmark, or an owner quality approval. The full model test record details the machine and limitations, and the separate source audit illustrates why automated passes need human review.

What would prove that the full task became more productive?

Conduct a new paired trial: draft each review manually and using AI, test both against the same acceptance standard, and log preparation, blocked waiting, checking, failed attempts, repairs, setup, upkeep, and an actual human quality decision. The three historical machine times cannot substitute for new matched manual and AI task observations.

Reproducible starting point: Download the six-case pilot instructions and blank timing and quality CSV. The inputs are fictional, and all measurement fields remain empty. After a real trial, run the existing offline workflow auditor. It checks arithmetic and reviewer-entered labels, not the truth of those labels.

Current evidence status: Historical model case execution was recorded. Comparable manual effort, human review and repairs, current model behavior, owner approval, recurring setup and upkeep, and total business cost remain unmeasured. No actual client deployment, time saving, error rate, or return on investment is claimed.

Inspect the source repository or read the owner approval checklist. Do not enter real customer or private business material into the public exercises.

Method / Measure the real task

What would it take to prove AI actually helped?

Measure preparation, generation, checking, repair, maintenance, and human approval. The first successful output is not the whole task, and an estimate is not an observation.

  1. Define the task and permitted inputs. Create an AI task brief.
  2. Preserve a credible non-AI baseline. Use a controlled workflow pilot.
  3. Verify important claims and numbers. Apply the source and arithmetic checks.
  4. Count human review and rework. Compare full workflow time.
  5. State the evidence level. Distinguish simulation, repeatable prototype, public release, repeated real-world use, and independently measured impact.
